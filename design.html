Gateway Infra – Stage 1 Design

A validated agent factory, tiered merging, and hard recovery guarantees

1. Stage 1 — A Validated Agent Factory

Stage 1 is a bounded-autonomy factory: AI agents can write and propose code, but every power they hold is scoped, revocable, and structurally separated. The goal is to let agents ship real work while making it impossible for a single agent — or a compromised one — to move unreviewed changes into the main branch.

  • Agent Server in a disposable VM. The agent runs inside a virtual machine that can be torn down and rebuilt at any time. Nothing of value lives only in the VM, so replacing it is routine, not an incident.
  • No Docker socket. The VM exposes no container control socket to the agent. The agent cannot spawn, alter, or escape host containers — its runtime is fixed by the factory, not chosen by the agent.
  • Loopback-only ingress. The agent server listens only on localhost. There is no inbound network path to the agent from the outside world; all external contact is outbound and mediated.
  • Inference bound to one local endpoint, fail-closed. Model inference is pinned to a single local endpoint. If that endpoint is unavailable, requests fail rather than falling back to some other provider — the agent degrades to "down," never to "unsandboxed."
  • Three least-privilege GitHub identities. The implementer can push branches but cannot approve its own work; the reviewer can approve but cannot merge; the merger can merge but cannot review. This structural separation means no single identity can carry a change from authored to merged alone.

2. Merge Tiers

Every path in the repository is assigned a merge tier that determines how changes to it may land. Higher-risk paths demand more human control; low-risk, well-understood paths can merge automatically — but only when every gate passes.

Tier Policy What it means
T0 Owner-gated paths Critical paths (security, infra, guardrails) are merged only by their human owners. Agents may propose; owners decide.
T1 Owner approval An owner reviews and explicitly approves the change before it is merged.
T2 Policy-driven auto-merge Merges automatically, but only when all gates pass: CI green, secret-scan clean, diff under size limits, changed paths on the allowlist, independent (non-author) review, and merge against the exact head SHA.

The T2 gates are cumulative, not alternatives. A failure in any single gate — a slow CI run, a secret flagged by the scanner, a diff that grew past its budget, a path not on the allowlist, a self-approval, or a branch that moved mid-review (head-SHA mismatch) — blocks the auto-merge. The merger identity executes the merge, but the policy, not the agent, decides when.

3. Recovery Guarantees

The factory is designed to heal itself quickly and predictably, so failures are boring:

  • Crash auto-restart in milliseconds. If the agent server or a guard process dies, the supervisor restarts it immediately. There is no manual step and no meaningful downtime.
  • Reboot convergence of the guard. On every boot, the system reconciles itself to the intended policy: firewall rules, endpoint bindings, and permissions are re-asserted until they match the declared state. A reboot cannot leave the machine in a weaker configuration.
  • Idempotent merges. Merging the same change twice returns the original commit rather than creating a duplicate. Re-runs, retries, and crash-replays after a merge are safe by construction.

Together these properties mean the system converges: after a crash, a reboot, or a retried operation, the factory ends up in the same correct state — agents sandboxed, guards enforced, and the repository history clean.
